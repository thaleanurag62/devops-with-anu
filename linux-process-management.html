Linux Process Management: ps, top, kill & systemctl

By Anurag Thale·Updated August 2026·10 min read

Every program running on a Linux system — from your shell to a web server to a background cron job — exists as a process. Learning to view, monitor, and control processes is one of the most practical skills you can build, especially when something on a server is misbehaving and you need to figure out why.

What is a process?

A process is simply a running instance of a program. Every process gets a unique Process ID (PID) when it starts, has a parent process that spawned it, consumes some amount of CPU and memory, and eventually exits (either normally, or because it crashed or was killed).

Viewing running processes: ps

ps                # processes in your current terminal session
ps aux              # every process running on the system
ps aux | grep nginx   # find a specific process by name

The output of ps aux gives you a snapshot with columns like PID, %CPU, %MEM, and COMMAND — everything you need to identify what's running and how much it's consuming.

USER   PID  %CPU %MEM    COMMAND
anu    1042  0.3   1.2    nginx: worker process
anu    2201  12.4  3.8    node server.js

Live monitoring: top and htop

ps gives you a one-time snapshot. top gives you a live, auto-refreshing view — sorted by CPU usage by default, so you can immediately spot what's consuming resources.

top          # live process viewer (built in on every distro)
htop           # nicer, color-coded, scrollable version (may need installing)
Tip: Inside top, press M to sort by memory usage instead of CPU, and q to quit. In htop, you can even scroll and kill processes directly with your arrow keys and F9.

Stopping processes: kill and killall

Every process can be sent a "signal" — a message telling it to do something, most commonly to stop. kill sends a signal to a process by PID:

kill 2201           # politely ask process 2201 to terminate (SIGTERM)
kill -9 2201          # force-kill it immediately (SIGKILL)
killall node            # kill all processes matching the name "node"

The difference matters: a plain kill sends SIGTERM, a polite request that lets the program clean up (close files, finish a database write) before exiting. kill -9 sends SIGKILL, which terminates it immediately with no chance to clean up. Always try a normal kill first — reach for -9 only when a process is truly stuck.

Background jobs: &, jobs, bg, fg, nohup

Sometimes you want a command to keep running without tying up your terminal:

long_task.sh &        # run in the background
jobs                    # list background jobs in this session
fg %1                     # bring job 1 back to the foreground
bg %1                       # resume a paused job in the background
nohup long_task.sh &          # keep it running even after you log out

nohup ("no hang up") is especially useful over SSH — without it, a background job typically dies the moment you disconnect from the server.

Adjusting priority: nice and renice

Every process has a "niceness" value from -20 (highest priority) to 19 (lowest priority), controlling how much CPU time the scheduler favors it with.

nice -n 10 ./backup.sh       # start a process with lower priority
renice 5 -p 2201                # change priority of an already-running process

Managing services with systemctl

Most modern distributions use systemd to manage long-running background services (web servers, databases, SSH). Instead of manually starting scripts, you interact with them through systemctl:

sudo systemctl status nginx      # check if a service is running
sudo systemctl start nginx         # start it
sudo systemctl stop nginx            # stop it
sudo systemctl restart nginx           # restart it
sudo systemctl enable nginx              # auto-start it on boot
journalctl -u nginx -f                     # follow its logs live

This is the standard way production services are controlled — Docker, Nginx, PostgreSQL, and most infrastructure tooling all register themselves as systemd services.

Why this matters in DevOps

When a server slows to a crawl or an application stops responding, process management commands are your first line of investigation: top to see what's eating resources, ps aux | grep to find a specific process, systemctl status to check if a service crashed, and journalctl to read why. This is the muscle memory that turns a stressful incident into a routine fix.

Key takeaways

  • Every running program is a process with a unique PID.
  • ps aux gives a snapshot; top/htop give a live view.
  • Prefer plain kill over kill -9 so processes can shut down cleanly.
  • nohup keeps background jobs alive after you disconnect from SSH.
  • Production services are managed through systemctl, not run as raw scripts.
